# 단체급식 프로모션 신청 서비스 PRD

> 상세 도메인 규칙/시나리오는 `doc/1-domain-definition.md` 참고. 이 문서는 개발 착수용 실행 문서이며, 1인 개발 3일 MVP 규모에 맞춰 필요한 내용만 담는다.

## 1. 개요 및 배경

영양사가 종이로 안내·수기로 취합하던 프로모션 안내와 참가 신청을 온라인으로 전환하는 서비스다.

핵심 흐름: **회원가입/로그인 → 영양사 프로모션 등록 → 취식자 조회·신청 → 영양사 신청 현황 확인**

## 2. 목표 및 성공 지표

- 목표 사용자 규모: 영양사(점포 관리자) 20명, 각 영양사가 관리하는 취식자 약 100명 (최대 약 2,000명)
- 핵심 성공 지표: **2,000명 이상의 취식자가 프로모션 기능(조회 또는 신청)을 이용**
- 이번 MVP는 지표 측정/통계 대시보드를 만들지 않는다. 지표는 서비스 오픈 후 DB 조회로 확인한다.

## 3. 대상 사용자

- **영양사(MANAGER)**: 프로모션 등록, 수정/삭제, 신청 현황 확인
- **취식자(PARTICIPANT)**: 프로모션 조회, 참가 신청/취소

역할별 상세 권한과 시나리오는 도메인 정의서 3, 8장 참고.

## 4. 범위

### 포함 (MVP)
회원가입 / 로그인·로그아웃 / 영양사·취식자 역할 구분 / 프로모션 등록·수정·삭제 / 프로모션 목록·상세 조회 / 참가 신청·취소 / 중복 신청 방지 / 모집 인원 제한(원자적 검증) / 신청 인원 및 신청자 목록 확인

### 제외 (Non-goal)
고객사/점포 관리, 복잡한 권한 관리, 비밀번호 재설정, 회원 탈퇴, 추첨/당첨자 선정, 쿠폰·리워드, 푸시 알림, QR 체크인, 댓글, 만족도 조사, 통계·분석 대시보드

전체 목록은 도메인 정의서 9장 참고. **이 범위 밖 기능은 3일 일정상 절대 손대지 않는다.**

## 5. 핵심 사용자 흐름 요약

1. 회원가입 시 이름/이메일/비밀번호 + 역할(영양사/취식자) 선택 → 로그인
2. 영양사: 프로모션 등록(제목/내용/신청기간/진행일/모집인원) → 목록에 노출
3. 취식자: 목록/상세 조회 → 신청(기간 내, 정원 내, 중복 아님) → 신청 완료/취소 확인
4. 영양사: 자신의 프로모션별 신청 인원·신청자 목록 확인

시나리오 상세는 도메인 정의서 8장 참고.

## 6. 기능 요구사항 요약

| 기능 | 우선순위 | 비고 |
| --- | --- | --- |
| 회원가입/로그인/로그아웃 | P0 | 이메일 중복 불가, 역할 선택 |
| 프로모션 등록 | P0 | 영양사 전용, 진행일 ≥ 신청 종료일 검증 |
| 프로모션 목록/상세 조회 | P0 | 취식자·영양사 공통, 모집/신청 인원 노출 |
| 프로모션 참가 신청 | P0 | 중복 신청 방지, 정원 초과 시 서버 원자적 차단, 마감 시 버튼 비활성화 |
| 신청 취소 | P0 | 본인 신청만 취소 가능 |
| 프로모션 수정/삭제 | P1 | 등록자 본인만, 신청자 있으면 정원 축소 불가, 삭제 시 신청 cascade 삭제 |
| 신청 현황/신청자 목록 확인 | P1 | 영양사, 본인 등록 프로모션만 |

상세 비즈니스 규칙(진행일 제약, 정원 축소 제한, cascade 삭제, 동시성 검증 등)은 도메인 정의서 4, 7장 참고. 여기서 재정의하지 않는다.

## 7. 비기능 요구사항

- **플랫폼**: 웹 우선. 별도 네이티브 앱 없음. 반응형 웹 UI로 모바일 브라우저 대응 (모바일 전용 최적화는 아님).
- **접근성(a11y)**: 이번 프로젝트 범위에서 고려하지 않음.
- **성능/동시성**: 신청 정원 초과 여부는 DB 트랜잭션/제약으로 원자적 처리 (동시 신청 경합 대비).
- **보안**: 비밀번호 해시 저장. 인증은 JWT 기반으로 access token(짧은 만료)과 refresh token(긴 만료)을 함께 사용. refresh token은 무상태(stateless)로 발급하며 별도 저장/무효화 테이블은 두지 않는다(로그아웃은 클라이언트에서 토큰 폐기로 처리). 그 외 보안 강화(재설정, 탈퇴 등)는 범위 외.
- **인프라**: 별도 구매 예산 없음. 로컬/최소 비용 배포 환경 전제.

## 8. 기술 스택 및 아키텍처 제약

- 프론트엔드: React 19, 전역 상태는 Zustand, 서버 상태/통신은 TanStack Query
- 백엔드: Node.js + Express
- DB: PostgreSQL 17, `pg` 라이브러리로 직접 접근 (ORM 없음)

**3일 일정에 대한 함의**
- ORM 없이 쿼리를 직접 작성하므로 테이블 수(User/Promotion/Application 3개)를 늘리지 않고, 쿼리도 CRUD 수준으로 단순하게 유지한다.
- 정원 초과 동시성 검증은 애플리케이션 락 대신 `UPDATE ... WHERE 신청인원 < 모집인원` 형태의 단일 쿼리 또는 DB 제약(트리거/체크)으로 처리해 구현 비용을 최소화한다.
- Zustand는 로그인 사용자 정보 등 최소한의 전역 상태에만 사용하고, 서버 데이터 캐싱/갱신은 TanStack Query에 위임한다.
- refresh token을 무상태로 처리해 별도 테이블을 두지 않으므로, 테이블은 User/Promotion/Application 3개로 유지된다.

## 9. 일정 및 우선순위 (3일, 1인 개발)

- **Day 1**: DB 스키마(User/Promotion/Application) + 회원가입/로그인 API·화면
- **Day 2**: 프로모션 등록/수정/삭제 + 목록/상세 조회 (영양사·취식자 화면)
- **Day 3**: 참가 신청/취소(중복·정원 검증 포함) + 신청 현황 확인 화면 + 반응형 점검

P0 기능을 Day 1~2에 우선 완성하고, P1(수정/삭제, 신청 현황)은 Day 2~3에 배치한다. 일정이 밀리면 P1부터 축소한다.

## 10. 리스크

- **일정 리스크**: 3일 내 1인 개발이라 버퍼가 거의 없음 → 범위 외 기능(4장 "제외") 요청이 들어와도 이번 MVP에서는 보류.
- **동시성 리스크**: 신청 마감 직전 동시 신청 시 정원 초과 가능 → 단일 원자적 쿼리로 검증해 리스크 축소.
- **인증 단순화 리스크**: 비밀번호 재설정/탈퇴 미지원으로 인한 운영 문의 발생 가능 → MVP 범위 외로 사전 안내.
